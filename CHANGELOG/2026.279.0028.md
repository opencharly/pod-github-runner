# 2026.279.0028 — fix(image): give the runner image hostname(1), and the tool surface the org's CI jobs actually call

## Summary

Closes #7. `check-githubrunner-pod` builds `ghcr.io/opencharly/githubrunner` — the image the
org's self-hosted runners execute jobs in. Three defects in it: two break the pool, one makes
the image lie about itself.

### 1. The image had no `hostname(1)`, so charly's own test-suite cannot pass on the pool

Verbatim from the `go` check-run of `charly#807`
([job 111961186574](https://github.com/opencharly/charly/actions/runs/37369026337/job/111961186574),
started `2026-10-05T20:19:41Z`, completed `2026-10-05T20:27:01Z` — **440 s**, inside the required
check's 600 s budget, so this is a real test failure and not a duration stall):

```
--- FAIL: TestInvokeProvider_VenueDescriptor_Venueless_ShellDescriptor (0.97s)
    plugin_dispatch_reverse_venue_test.go:155: venue-less + shell descriptor peer result: {Status:pass Message:peer-executed Stdout: Stderr:bash: line 1: hostname: command not found
         Exit:127}
    plugin_dispatch_reverse_venue_test.go:161: peer executed on the WRONG host: got "" want "charly-githubrunner-no-2" (host-local materialization failed)
```

charly's venue descriptor shells out to `hostname` to prove a peer ran host-locally. The
runner image carried `coreutils`, but Arch's `coreutils` ships no `hostname` — it lives in
`inetutils`. The test therefore fails for the image, not for the code under test, and every
repo whose CI runs `go test ./...` on the pool inherits the red.

The fix is the package plus the check that would fail without it:

```yaml
- check: hostname(1) resolves on PATH, so charly's venue tests can prove a peer ran host-locally
  id: gr-hostname
```

### 2. The image was missing most of the tool surface a CI job reaches for

24 further packages, **each with its own `package=<name>` check in the plan**, so a
declared-but-missing tool fails the image build rather than a job at 02:00: `tree` `shellcheck`
`shfmt` `actionlint` `golangci-lint` `nodejs` `npm` `python-pip` `uv` `cmake` `unzip` `zip`
`7zip` `wget` `rsync` `yq` `ripgrep` `moreutils` `bc` `less` `lsof` `strace` `openbsd-netcat`
`bind`, plus `LANG=C.UTF-8` / `TZ=UTC` with the two checks that assert them.

None of these names existed in the candy before — measured against `origin/main`:

```

    printf '%-12s origin/main=%s  HEAD=%s\n' "$p" \

```

My first draft of this PR justified `LANG=C.UTF-8` by claiming "Python 3 falls back to ASCII
as the filesystem encoding, so a job that touches a non-ASCII path fails". Probing the built
image disproved it — CPython ≥ 3.7 coerces the C locale itself — so the claim is gone from
the candy, its skill entity and this body rather than shipped (R1). What the probes did show,
with `LANG` unset:

```
$ podman run --rm --entrypoint env ghcr.io/opencharly/githubrunner:check-githubrunner-pod-2026.279.0009 -u LANG -u LC_ALL bash -c \
    'locale -a; locale charmap; python3 -c "import locale,sys;print(locale.getpreferredencoding(False), sys.getfilesystemencoding())"'
C
C.utf8
POSIX
ANSI_X3.4-1968
utf-8 utf-8
```

So: the image generates no locale, a non-login process lands in POSIX and its codeset is
ASCII, and Python is emphatically *not* the victim. The image already has `/etc/locale.conf`
naming `C.UTF-8`, but that reaches only login/PAM sessions, and a charly `check` and a job
process are neither — the `env:` declaration is what applies, which is precisely why the
`locale charmap` check genuinely fails when it is removed. `C.UTF-8` is built into glibc, so
nothing needs generating. The `TZ` check asserts the *variable* (`printenv TZ`), deliberately
not `date +%Z`: the image's
`/etc/localtime` is already UTC, so a `date`-based check would pass either way and prove
nothing.

### 3. The skill entity documented a knob that does nothing, and omitted the one jobs select on

The `| Variable | Mechanism |` table in this candy's own skill entity carried
`| RUNNER_GROUP | Default |`. The candy declares `RUNNER_GROUP` in `env:`, and **nothing reads
it**: the registration hook passes `--name`/`--labels`/`--work` and never `--runnergroup`, and
no other repo in the org sets or reads it either — `git grep RUNNER_GROUP` over the umbrella
returns only the declaration and copies of this table. Its mirror image is `RUNNER_LABELS`,
which the hook *does* consume (`--labels "${RUNNER_LABELS}"`) but which was declared nowhere,
so the one value every self-hosted job selects on had no supported way of being set.

Because this PR extends that very table with the `LANG`/`TZ` rows, the dead row is this PR's to
cure rather than something to build on top of (R2, R5, and the reviewer's B14(c)).
`RUNNER_GROUP` is deleted — env declaration, skill-table row and README row, in this commit.
Wiring it instead would have been an unprovable runtime change: `config.sh --runnergroup` is
org-only, so consuming it would break the user/repo-level registration the `RUNNER_ORG`
description advertises, and the token-guarded hook can never be exercised by a bed.
`RUNNER_LABELS` becomes an `env_accept` entry beside `RUNNER_ORG`.

**This deviates from the plan I filed on #7, on purpose.** #7 predicted the fix would need its
own PR *after* this one, on the grounds that a registration-hook change is not bed-observable.
Deleting a dead `env:` entry and declaring a live one is not a hook change — the hook is
untouched, byte-identical — and it *is* bed-observable, because both halves show up in the
built image's labels, which the R8 read-back below reads from the real artefact. Folding it in
is also what R2 requires: this PR edits the very table that carried the dead row, so a separate
PR would be parking a defect this one is standing on. #7 is updated with a `STATUS` saying so,
and it closes with this PR.

Behaviour is unchanged: the hook's `: "${RUNNER_LABELS:=opencharly}"` fallback still yields
`opencharly` when nothing sets it, so the registered label set is byte-identical to before.
