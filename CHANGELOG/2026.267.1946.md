# 2026.267.1946 — docs(skill): org-runner routing causes + the gh requirement

## Summary

Adds two operational sections to the `github-runner` skill, each proven while
deploying a self-hosted **org** runner.

**Org-runner routing — a queued job is almost never an agent problem.** A job
showing `labels: ["<label>"]`, `status: queued`, `runner_name: ""` while the
runner reads `online` + `busy: false` is a routing failure. The section lists
the three causes in order:

1. **The runner group does not allow public repos (the silent one).** A group
   with `allows_public_repositories: false` makes its runners INVISIBLE to every
   public repo in the org — jobs queue forever with no error anywhere. The fix
   needs a REAL boolean: the `gh` `-f` flag sends the string `"true"` and the API
   rejects it (`"true" is not a boolean`), so `--input <json>` is required.
2. **A `labels` mismatch** — including a `vars.` label a reusable workflow
   resolves (e.g. `vars.REVIEW_RUNNER_LABEL`).
3. **A stale broker session** after a container restart:
   `TaskAgentSessionConflictException` / `A session for this runner already
   exists`, retrying on a 30s loop while still reporting `online` — cleared by a
   full `charly remove` → `charly config` → `charly start` cycle, not a restart.

**`gh` must be present for a review/gate runner.** The org `pr-validator` drives
`gh api` / `gh pr comment` / `gh pr merge`; compose `/charly-tools:gh` (it is not
part of the base toolchain).

```
$ gh api /orgs/opencharly/actions/runners --jq '.runners[0]|{name,status,busy}'

# ...after PATCH allows_public_repositories=true...
{"name":"charly-githubrunner","status":"online","busy":true}     # now taking jobs
```
